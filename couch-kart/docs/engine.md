# Engine

Covers `game/main.c`, `game/proj.asm`, `game/data.asm`, `tools/tracks.py`, `tools/gen_assets.py` and `tools/characters.py`: how the split-screen Mode 7 picture, the menus, the select screen, the tracks, the kart types, the race rules, the cup and the things on the track are made, and the rules that keep them working.

## Screen

- 224 lines. Lines 0-111 are player 1, 112-223 player 2. Each half is 24 lines of sky, then 88 lines of floor (`SKY_LINES`, `FLOOR_LINES`, the same values in main.c and gen_assets.py).
- The floor is the one Mode 7 background: a 1024x1024 map of 8x8 tiles, at most 256 unique tiles, 256 colours. The sky is a map tile, not the backdrop colour, because snes9x2002 draws the backdrop colour wrong (cyan sky, red menus); the title and results screens fill their background with an opaque colour for the same reason.
- Mode 7 has a single background, so anything else on screen (karts, lap counter, positions, items) is a sprite. The hardware does not clip sprites to a half: the game hides any sprite whose 32-line box would cross into the other half.

## How the floor gets its perspective

- For floor line `l` the tables hold `s(l) = HC/(l+K0)` (map pixels per screen pixel sideways) and `t(l) = s*FOCAL/(l+W0)`, each multiplied by cos of each of 128 steering angles, as 8.8 fixed point (`persp_s.bin`, `persp_t.bin`, 22 KB each).
- The matrix per line is A = s·cos, B = t·sin, C = s·sin, D = −t·cos. Sine and minus cosine are cos at angle −32 and +64, so two tables cover all four values.
- Six HDMA channels write, on every line: M7A to M7D (indirect HDMA, each pointing into a table row for the player's angle), the scroll registers, and the centre registers. The CPU only picks table rows (`camera()` in C) and fills six small tables in RAM (`init_hdma` in proj.asm, every race frame).
- HDMA takes about a fifth of every display line from the CPU, so code that runs during the picture is slower than its cycle count suggests.
- Sky lines read a zero word stored before each table and centre on the sky-blue tile at map tile (127,127). That tile is reserved: no track may draw there.
- The camera sits `D0` = 57 map pixels behind the kart, which is where floor line 84 lands; the own kart sprite is drawn with its wheels on that line.
- `tools/m7_model.py` renders the floor from the same RAM tables with the hardware formula. Comparing it with the emulator picture proves the hardware draws what the tables say, not that the tables are right. The test checks the tables from outside: the floor under each kart sprite must be the kart's map position, and the floor near the horizon must lie ahead of it.

## PVSnesLib quirks

Each one was found by a picture that did not change, and confirmed in emulators.

- DMA channels 0 and 1 are the library's. HDMA on channel 1 hangs the frame loop.
- The library's vblank code undoes the HDMA set-up, so `init_hdma()` sets every channel register on every frame, right after `WaitForVBlank()`. Set up once, the floor stays flat.
- A pointer to a global reports bank 0, but globals live in bank $7E; HDMA tables in RAM use bank $7E explicitly.
- I/O registers are written through constant addresses (the `HDMA_CHANNEL` macro). An address computed at run time does not reach the register.
- tcc-816 `int` is 16 bits. Products that can exceed 32767 are halved first; there is no 32-bit maths in the frame loop.
- tcc-816 puts some `const` arrays in initialised work RAM instead of the ROM (two-dimensional ones). They work, but a test reading such a table reads work RAM (`rom_bytes()` in the tests handles both). The per-track tables in `res/tracks.h` are flat for this reason.
- tcc-816 can compile an early return on `a || b` the wrong way round: `if (battle != 1 || !balloons[p]) return;` ran the body when `battle != 1` (a third hit in any race ended it). Write such guards as separate `if`s; the compiler's "ERROR no jump found to patch" comments appear everywhere and do not mark the bad ones.
- `make` exits 0 even when the link fails, and the old ROM stays: `scripts/check.sh` and `tools/break_rules.py` also require "Build finished successfully" in `game/couchkart.log`. A direct-page operand in proj.asm needs `<` (`lda [<ms_sp],y`), or the link fails this way.

## Speed

- The ROM is FastROM (`FASTROM := 1` in `game/Makefile`): code and tables are read from banks $80 and up at 3.58 MHz instead of 2.68. It bought about a quarter more logic per frame (measured).
- tcc-816 C is slow: about 5 lines for one sprite write and 26 for one projected object (measured). The hot paths are hand-written in `game/proj.asm`: `spr()` (a sprite write, about 1 line), `camera_both()` (each player's camera and table rows, from two tables per angle in `cam.bin` instead of multiplies; `camera()` does one), `draw_objects()` (the other kart, the shots and the obstacles in both halves), `move_shots()` (also the leader shot's flight), `move_obstacles()` (each tests a shot or obstacle against every racing kart with one subtraction and compare a kart and axis, written out kart by kart with the racing count checked between karts; a shot in its first 20 frames goes through `ms_try`, which spares its thrower), `minimap()` (the karts' dots), `drive()` and `move_kart()` (speed, steering, the move; `mk_move` reads each axis's step, sin of the heading times the speed, from `mk_tab`, a table of 128 headings by 64 speeds of signed 16-bit words made by `step_table()` in gen_assets.py, 16 KB, instead of multiplying: it saved 3 lines on the busiest frame with 3 computer karts, 5 karts move each frame; no kart is faster than 62, and the routine clamps the column at 63), `progress_players()` (the lap-progress lookup for both players, bits for a lap and a sign change each; `progress_cpu()` does it for one computer kart a frame, each every 4 frames, and returns the karts that reached a lap or whose sign changes as bits), `slipstream()`, `init_hdma()`, `lap_next()` (a kart reached checkpoint 0: the lap count, and past `LAPS` the finish: place, the 10 s and 1.5 s timers, `winner`, the player's banner armed; then `prog`; the C draws the lap counter and the final-lap banner only when it returns 0), `banner_step()` (the next 2 glyphs of a half's finish or final-lap banner, from a table of OAM bytes), `frame_lines()` (the line counter as `measure()` reads it, for the computer karts' item decisions), `clock_step()` (the random number, and once the countdown is over the race clock and the banner timers), `busy_flags()` (a bit per player job that has anything to do: `own_kart()`, `effects()`, `banner_step()`; the usual frame calls none of them, which cost 9 lines in C), `cpu_frame()` (every racing computer kart drives: see Computer karts; it shares `dr_run`, the body of `drive()`, with the players' call), and these that loop over every kart (and pair of karts): `kart_timers()` (the plain countdowns: spin, trick, wheelspin, shield, star, and a computer kart's item decision countdown `cpu_use_t`, which sets the kart's bit in `cpu_due` at 0; returns the karts whose shield ended, for the C to take its picture away), `ground_all()` (the floor's work after the move, see Things on the track, and the shrink's countdown; returns the karts whose fall ended, for `rescue()` in C) and `floor_scan()` (returns the karts on the ground whose floor cell holds a coin, panel or slime; `floor_things()` in C runs only for those), `bump_all()` (every pair of karts closer than 10 px on both axes is pushed apart along the axis it overlaps least on, the x axis on a tie, and both lose a quarter of their speed; a kart in the air or sinking touches none; returns the karts a star kart touched, for `hit()` in C), `keep_all()` (every kart held on the map, at most speed 3 after touching an edge) and `rank_all()` (each kart's place: 1 plus the karts with more progress, or equal progress and a lower number; a kart that finished keeps its finishing place, and one still racing counts it ahead since its progress is the larger; writes `place[]` and returns the karts whose place changed, for `hud_place()` in C; with computer karts racing it works one kart in four a frame: karts 0 and 4 when `race_time` & 3 is 0, 1 and 5 on 1, 2 on 2, 3 on 3, so each every 4th frame, which spreads the 8 lines of working all six out). All loop over the karts racing, `nk_n` = 2 + `cpu_n` (the `LOAD_NK` macro sets it, `nk_w` and `nk_off` at the start of each; `NKARTS` 6 is the number the data holds; `bump_all()` has one unrolled copy of its pair tests for each racing count, 2 to 6, and tests each pair with one subtraction and compare against the first kart's position plus 10 px before the slow path pushes the pair apart) with a byte index for the per-kart arrays and a 12-byte offset into `karts` (the tables `kart_off` and `kart_bit` for a kart's offset and bit); results come back as a bit per kart in `tcc__r0`. `steer_fast()` turns one homing shot a frame with the hardware multiplier (`smul`, a signed 8 x 8 product), and, for the rare shot whose step no longer matches its heading (it bounced or turned at a corner), first takes the heading that fits: up, down, left or right when one step is 0, else the mirror, a quarter turn back or a quarter turn on; a shot that fits none flies straight (`shot_home` 0). `kart_frame()` skips `roll_step()` and `tricks()` unless a roll, a hop, a drift or L or R pressed needs them, and `race_frame()` does not call it at all unless a player has a roll, a hop or a drift or presses X, L or R (saved a line on the busiest frame). In a routine that mixes `sep` and `rep`, a label after a jump must start with its own `sep` or `rep` when the code that reaches it is in another width than the code written above it, because the assembler tracks the width by reading downwards: a wrong guess assembles an immediate one byte too long and the program misbehaves without an error.
- Avoid `*` and `/` by a variable or a signed value in per-frame C, because tcc-816 calls a runtime routine for them (a table, like `drop_d` for where slime drops, is cheaper). They follow the tcc-816 convention: arguments on the stack from `4,s` (`6,s` after `php` and `phb`, `8,s` after `phd` too), A, X and Y 16 bits on entry and exit, any register free; a result goes in `tcc__r0` (address 0), because the C reads it there and ignores A. They set the data bank to $7E for the C globals and reach I/O registers with long addresses; `draw_objects` and `move_shots` also point the direct page at their own variables (`pj_base`, aligned to 256 bytes in low RAM) and restore it.
- Measured (busiest frame, `max_lines`, of 262 lines, on snes9x2002, snes9x2005 and snes9x): 145, 151 and 156 before the make-room step with no computer karts, 127, 132 and 137 after it. What gave the lines, most first: `move_shots()` and `move_obstacles()` testing each kart with a macro per kart (11 to 16 lines on the busiest frame with 4 karts), the quick-outs in `busy_flags()` (9 lines a quiet frame, with `own_kart()`, `effects()` and `banner_step()` called only when needed), `bump_all()` unrolled (3 to 4), `lap_next()` and `banner_step()` in assembly (the finish frame lost 5), `steer_fast()` taking the slow path (6 on a bounce), and `rank_all()` spread over four frames (the frame that worked out all six places cost 8 lines more than the others).
- Per-phase readout: `python3 tools/test_rom.py --phases` builds a copy of the ROM with `PROBES` set to 1 in main.c and prints, per emulator, what each phase of the busiest frame cost. `probe()` (proj.asm) stores the line counter (4 reads of I/O registers, a latch and the two bytes of the vertical counter) into the next word of `phase_line[]` at 21 points of `main()` and `race_frame()`; `measure()` copies the table to `phase_best[]` on a frame that sets a new `max_lines`. One probe costs about 0.45 line (the 21 probes add 9 to 10 lines to the busiest frame with computer karts), so the release ROM and the normal test have `PROBES` 0 and the probes compile to nothing; the cost of each probe sits inside the phase it ends, so every figure includes about 0.5 line. The frame that sets the maximum differs a little between builds, so a change of 1 line in one phase is noise. It also prints the phases of the computer-kart busiest frame with 1, 3 and 4 karts, each with `cpu_alt` 0 and 1, and never stops on the budget checks (the normal run does). The 20 phases, in order: vblank work, clock and timers, items and drive (the players), the computer karts driving, ground, bump and map edge, camera, floor things, steering the homing shots, moving the shots, obstacles and hits, slipstream, panels, the players' laps, the computer karts' laps, places, banners and the own kart and effects, minimap, `draw_objects()`, battle clock and the computer karts' item decisions. On snes9x with 3 computer karts driving and `cpu_alt` 1 (probes included, 189 lines, in the costly scene of the Computer karts section): 5, 5, 12, 18, 6, 5, 3, 4, 4, 13, 5, 1, 1, 5, 4, 4, 2, 3, 82, 1; the projection is 45 percent of it, then the computer karts' driving (18), the two players' driving (12 with their item work), the shots (13 plus 4) and the hits (5).

## Screens

- `game_state`: title (0), results (3), the select screen (4), the track menu (5) and the podium (6) are Mode 1 screens with one background; countdown (1) and race (2) are Mode 7. Title, then select, then the track menu (the cup or one of the four tracks; Y goes back), then the race. From results, Start races the same track again, or in a cup the next track, and after the fourth the podium; Select returns to the select screen. From the podium, Start begins a new cup and Select returns to the select screen.
- The track menu keeps the select screen's sprites: both picked portraits show; its cursor is a ">" written to the map in vblank. Row 23 reads "COMPUTER KARTS: 3" (a blank row above it and below it, then two help lines on rows 25 and 26, the second reading "LEFT/RIGHT: COMPUTER KARTS"); the cup, the four tracks and the two battles are on rows 9 to 21, two rows apart. Left or right on either pad counts the number of computer karts (`cpu_menu`, 0 to `CPU_MAX`, wrapping at both ends; `CPU_MAX` at power-on, kept through races, battles and cups until the power goes off), whichever row the cursor is on, except a battle row: there the line reads "COMPUTER KARTS: NONE" and left and right change nothing. The menu copies it into `cpu_n` when a race or cup is chosen, and `start_race()` sets a battle's to 0, so the choice stays. The label is written with the screen off; a change rewrites only the 4 characters after it (a whole-line rewrite overran vblank on snes9x and the number showed late).
- The cup: `cup_on`, `cup_race` (0-3, also the track), `points[6]` (a kart each). `show_results()` adds points from the table `cup_points` in main.c: with `cpu_n` 0, 3 for first and 1 for second only when it finished; with computer karts every kart that finished scores by its place, 9, 6, 4, 3, 2, 1 for places 1 to 6 (the table has the sixth place so a larger `CPU_MAX` cannot read past it), and a kart that did not finish scores 0. A cup keeps its two computer animals (`cpu_pick`) from its first race to its fourth: `choose_cpu()` picks them only when it is not a cup's later race (a single race picks again each time).
- Results: with `cpu_n` 0 the two players, the winner first, with their pictures (rows 11 and 16). With computer karts: no pictures, and one row of two text lines for each kart in place order (`place`), three text rows apart from row 9 (so 5 karts end on row 22): place and animal on the first line with the time (or "NO TIME" for a kart that did not finish, as in the two-player results), "PLAYER 1", "PLAYER 2" or "COMPUTER 1" to "COMPUTER 3" under the animal (a computer kart is numbered by its kart number, kart 2 being computer 1, so two computer karts of one animal can be told apart; the podium uses the same names, `driver_name[]`) and the cup points under the time; the big "WINS!" line names the animal in first place; START and SELECT move to rows 24 and 26. Karts still racing when the race ends are placed behind the finishers by progress and show "NO TIME". `rank_all()` works out one kart in four a frame with computer karts, so `show_results()` first calls it once with `rk_full` set, which works out every kart: no two karts share a place on the screen. With `cpu_n` 0 the results rows are as before; the balloon and coin battle results put the count ("3 COINS") on the driver's line (row + 1) at column 22, so it never runs into the longest animal name (11 letters from column 11) on the line above.
- The podium: `show_podium()` ranks the karts by points, a tie going to the better `place` in the last race, and fills gold (1st), silver (2nd) and, with computer karts, bronze (3rd) blocks (tiles 176, 177 and 178 after the big letters in `ui.pic`). With `cpu_n` 0 it is the two-player podium (silver at column 4, no third block, the players' race pictures). With computer karts the three blocks sit at columns 12, 1 and 23 (rows 15, 18 and 20) and each shows its animal's 32x32 portrait, with "PLAYER 1", "PLAYER 2" or "COMPUTER n" on the block under it (centred on the block, two rows below its top), and the points below the blocks as "23 PTS" starting at columns 13, 2 and 24, so the three texts have at least two blank columns between them, so the select screen's portrait tiles and palettes are loaded into sprite memory first (a computer animal has no race picture of its own); the next race reloads the race sprites. Computer karts 2 and 4 share an animal, so one animal can stand on two blocks. `cup_winner` is the kart on the gold block.
- VRAM in words: Mode 7 map and tiles 0-0x3FFF, Mode 1 background tiles from 0x4000 (at most 384 tiles), Mode 1 map 0x5800, sprites 0x6000-0x7FFF. The Mode 1 screens never touch the Mode 7 data. The select screen loads its own background tiles and sprites over the letters and the race sprites, so `start_race()` reloads the race sprites (`load_race_gfx()`).
- The select screen's background is one picture drawn by `select_background()` in `gen_assets.py` (heading, a panel in each animal's kart colour, names and kart types in a small font, the controls), cut into tiles with a palette each. Portrait i sits at `SEL_X + 40 * (i % 6)`, `SEL_Y + 56 * (i / 6)` in both files.
- A mode switch turns the screen off and runs after `measure()`, because it takes more than a frame.
- Mode 1 text is written to VRAM through the data port while the screen is off: a DMA from a RAM buffer would read bank 0 (see the pointer quirk below).

## Sprites

- 16x16 small and 32x32 large, 512 tiles from 0x6000 in a sheet 16 tiles wide.
- In a race: tiles 0-127 are player 1's animal and 128-255 player 2's, each copied at race start from that animal's 4 KB block (near views 0-3 in the first 4 tile rows, near view 4 and the 10 small frames in the next 4); tiles 256-511 hold the countdown and the glyphs, and after GO the computer karts' frames (below). `gen_assets.py` writes the tile numbers to `res/layout.h` from the same functions that place the frames, and the tests compute them the same way, so the three cannot drift.
- On the select screen: the 18 portraits as 32x32 frames (tiles 0-319), then the cursor halves (320-335).
- Karts and drivers come from 3D models in `tools/characters.py`, drawn from 5 angles (back, back-side, side, front-side, front) at 3 sizes, plus a 32x32 portrait without the kart; the other 3 angles are mirrors. Each animal takes about 20 s to render, so `game/res/characters.cache` keeps each animal until its model, its palette or the renderer changes; a fresh clone renders all 18, which is the slow part of a first build.
- `spr()` (proj.asm) writes the library's OAM copy directly and `hide()` moves a sprite to line 224, where a 32-line sprite does not wrap to the top. The sprite shows a frame after it is written: the library sends the OAM copy at the next vblank, so a screenshot taken right after moving something shows it where it was.
- Race sprite slots: 0-1 the own karts, 2-3 the other kart in each half, 4-23 the HUD, 24-39 the countdown, finish and final-lap banners, 40-43 and 44-47 the shots in player 1's and player 2's half, 48-55 each half's item picture, coin and coin count, 56-59 the sparks or flame at each own kart, 60-61 and 62-63 the obstacles in each half, 64-67 the players' minimap dots (player 1's kart in the top half, player 2's, then both in the bottom half), 70-71 each half's wrong-way sign, 72-75 the balloons in a balloon battle (in each half the own kart's, then the other kart's: `BAL_SLOT`), 76-79 and 80-83 the computer karts in player 1's and player 2's half, 84-87 and 88-91 their minimap dots (top half, then bottom half), 92-93 each half's minimap (`MINI_SLOT`; `SLOTS` 94; 68 and 69 are free). A lower slot draws in front: the minimap sits after every dot so the dots draw on top of it, and the other player's kart (slot 2 or 3) is in front of the computer karts. The high OAM bits of the shots (bytes 522 and 523), the obstacles (527), the players' dots (528), the computer karts (531 and 532) and their dots (533 and 534) are cleared at race start and never written, because those are always small with x below 256.
- Shared race tiles hold, after the glyphs and the flag, each player's HUD item frame and the shot (`ITEM_ART`; the 14 HUD pictures live in the ROM, `items.pic`, and `load_hud()` copies the one shown into the player's frame in vblank), then the coin, the shot at mid and far distance, two spark and two flame frames (`EFFECT_ART`), then the wrong-way sign, the obstacle at three sizes and the two minimap dots (`TRACK_ART`). Four small frames there form one 32x32 block at tile 460 (`TILE_MINIMAP`), which each race fills with its track's minimap (4 rows of 128 bytes). The two small frames that used to be free hold the R of "3RD" (tile 426, `TILE_GR`, drawn like the HUD letters, which have no R) and a computer kart's minimap dot (tile 490, `TILE_DOT3`: a white square with the dark ring). Both are in `shared.pic`, so they are there from the race screen on, during the countdown.
- Computer karts' pictures: a computer kart is never an own kart, so it gets only its animal's mid views 0-4 and far views 0, 2 and 4 (8 small frames, 32 tiles), and the mid frames serve the near size too (half the own kart's scale). They live in the countdown's big-digit tiles, which nothing shows once GO's 60 frames are over: animal A in tile rows 16-17 (tiles 256-287) and animal B in rows 18-19 (288-319), each a band of two tile rows 16 wide (frames at tile `CPU_BASE + 32 a + 2 i`, mid views 0-4 as i 0-4, far views 0, 2, 4 as i 5-7). `choose_cpu()` picks the two animals at every race start (a race or a cup race, not a battle) from the animals neither player picked, different from each other, by `rng`: the (low byte mod 16)th free animal, then the (high byte mod 15)th of those left; they are `cpu_pick[2]`. `load_cpu_gfx()` (main.c, in the vblank work of `main()`) copies one animal a frame once `game_state` is the race and `timer` is 0, which is the frame after the GO banner is hidden: 6 `dmaCopyVram` calls of 384 and 64 bytes (the runs `cpu_copies()` in gen_assets.py works out, written into `layout.h` as `cpu_src`, `cpu_dst`, `cpu_len`), counted in `cpu_loaded`; `cpu_gfx_ready` is 1 when both are in video memory, and the drawing must check it before it shows a computer kart. A frame that copies costs about 17 to 19 lines more than a quiet frame (measured, 76 to 94 lines, on three emulators), which lands in the first seconds of a race, far from the busiest frame. The "O" of GO (rows 20-23, columns 0-3, 16 tiles) holds the leader shot's picture once GO is gone: `load_leader_gfx()` (main.c, the vblank work of `main()`, called before `load_cpu_gfx()` so its four copies of 128 bytes, one tile row each from `leader_pic` in `leader.pic`, land on a frame of their own) copies it when `timer` is 0 and the computer animals' frames are in (or in a battle, which has none), and sets `leader_ready`; `choose_cpu()` clears it at every race start. Near, mid and far frames of the comet sit at tiles `TILE_LEADER`, +2 and +32 (`leader_tile()` in gen_assets.py); the fourth 16x16 block is free. The shot cannot be fired before `leader_ready` (the item is kept), so its sprite never shows while the tiles hold the O. A rematch or the next cup race reloads the whole shared block with the screen off, so the digits are back for its countdown.
- Sprite palettes in a race: 0 player 1's animal, 1 player 2's (each animal's own 16 colours, from `cast_pal`), 2-4 text in white, yellow and green, 5 the items, effects and wrong-way sign (`ITEM_PAL`), 6 and 7 the two computer animals (`cpu_pick`, from `cast_pal`, loaded by `load_race_gfx()`). Every animal's palette has the same slot layout (`tools/characters.py`), so an animal's frames drawn in the other computer animal's palette are a recolour: computer kart 2 is A in palette 6, kart 3 B in 7, kart 4 A in 7, kart 5 B in 6. The white text palette 2 also holds, in its unused entries, what had palettes of their own: entries 6-9 the minimap (outline, road, player 1's blue, player 2's red; `MINI_FIRST`), also the balloons' outline, highlight, blue and red, and entries 10-14 the track's five obstacle colours (outline, main, shade, stripe, highlight; `OB_FIRST`, loaded by `load_track()` at colour 170 from the track's 10-byte `obpal`). Their pictures use those entry numbers (`ART_REMAP`, `MINI_MAP`, `BALLOON_MAP` in gen_assets.py), so the minimap, its dots, the obstacle and the balloons are drawn with palette 2 (`PAL_MINI` is 2). `shared.pal` holds palettes 2-5 only (128 bytes). The star flash still uses the yellow palette 3.
- Sprite palettes on the select screen: 0-5 the portraits, three animals each in cast order (outline, white, then skin, skin shade, belly and one accent per animal; `portrait_palette()`), 6 the cursors. Mode 1 has 8 background and 8 sprite palettes, so 18 full palettes cannot show at once; the portrait is the animal re-coloured into 4 of its own colours.

## Kart types

- `kart_types[3]` in main.c holds, for light, medium and heavy: speed gained per frame (in 1/16 of a step, carried in `accel_frac`), top speed on the road and steering per frame. `drive()` reads the row for `kart_type[p]`, set from the animal at race start. Grass caps every kart at 16.
- Measured on three emulators: light reaches top speed 39 in 32 frames and turns 176 a frame; medium 40 in 40, 160; heavy 41 in 55, 144.

## Tracks

- Four tracks, each a description in `tools/tracks.py`: a centre line in race order from the start line (control points for a smooth curve; the oval keeps its octagon), a road width, a look (the colours of a shared palette layout: sky, off-road light and dark, road, curbs), and its things: coins, 4 item panels, boost pads, ramps, oil, sand drifts, water, a crevasse, at most 2 obstacles and an optional sandy shortcut. `draw()` makes the 1024x1024 picture, a surface value per 8x8 tile, the lap progress per 16x16 cell, the rescue point of each checkpoint, the start grid (six places: the players side by side 20 px before the line, then the computer karts in two rows 44 and 62 px before it; the players stand 12 px each side of the centre line, the computer karts at -18 and 18 (row 44) and 0 and 18 (row 62), `GRID_BACK` and `GRID_SIDES`, so none starts in a player's line (the road leaves room for no more than 18 and 19 px; the oval's places are written out in the generator); the generator stops when a place is not on plain road or lies on a coin, panel or pad cell, and the row at 62 px stops short of the Frosty Peaks crevasse, which ends 71 px before the line) the steering map for the computer karts (below) and the minimap. `python3 tools/tracks.py DIR` writes a preview PNG of each track and one with the steering map's arrows over it (`trackN-steer.png`: a line from each cell's centre along its heading, red where the kart slows).
- `gen_assets.py` cuts each picture into 8x8 tiles. Curved edges make 870 to 1,220 unique tiles, more than Mode 7's 256, so `reduce_tiles()` keeps the most-used tiles and the most different edge tiles and swaps each other tile for the nearest-looking kept one (plain grass, dark grass and road always stay). Coins, panels, slime, pads and ramps are painted after, as exact 16x16 pictures.
- In the ROM each track has its tiles, map and surface map in sections of their own and the rest (palette, starting cells, lap progress, minimap, obstacle colours) in a fourth (`res/tracks.asm`); `res/tracks.h` has pointers to them (`trk_tiles[]` and so on) and each track's facts as flat tables: floor cell pictures, panel cells, grid, heading, rescue points, obstacles. `load_track()` at race start copies the tiles (the high byte of each VRAM word), the map (the low byte), the palette, the minimap and the obstacle colours, and points `cur_map`, `cur_surf`, `cur_cells`, `cur_prog` and `cur_steer` at the track's data. The ROM is 512 KB, about 503 KB used.

## Things on the track

- Coins, item panels and dropped slime are painted into the floor map, one 16x16-pixel cell (2x2 tiles) each. `cells[4096]` in RAM holds what lies in each cell (0, coin 1, panel 2, slime 3), copied from the track's starting cells at race start, so a kart finds what it drives over with one read. `floor_set` (RAM, copied from the track) holds the 4 map tiles of each cell picture: road, coin, panel, slime on road, light off-road and dark off-road. Slime is dropped only on road or off-road, not on sand, water, oil or a ramp.
- A changed cell is queued (`queue_cell()`, two map writes) and written by `flush_map()` right after `init_hdma` in vblank, the only time VRAM takes writes. The Mode 7 map is the low byte of each VRAM word, so it is written with VMAIN 0. A race start reloads the whole map with `dmaCopyVram7` while the screen is off.
- Surfaces, one byte per 8x8 tile (`SURF_*`): 0 off-road (grass, dunes, snow), 1 road, 2 boost pad (a short boost), 3 ramp, 4 oil, 5 sand (slows to the off-road speed like grass), 6 water or crevasse. `drive()` reads the speed rules; `ground_all()` (proj.asm) runs after the karts move: a ramp lifts the kart for one frame per speed step (8 to 56 frames, so a jump covers speed x speed / 16 px), in the air the kart keeps its speed and the floor does nothing, L or R in the air turns it once round (the ramp trick) and gives a 40-frame boost on landing; oil spins it at speed 24 or more (`OIL_SPEED`, no coins lost; a kart that spun to a halt on the patch crawls out instead of spinning again each time its spin ends, which held a kart there for good); water or a crevasse stops it, it sinks out of sight (smaller frames, then hidden; the other half stops drawing it) and after 1 s `rescue()` puts it at its last checkpoint's rescue point, facing on, 2 coins lighter. A rescue point is the middle of the checkpoint on plain road, moved back to 130 px before a ramp when it lies on the run-up, the ramp or just past the gap, so a rescued kart gets up to speed and must jump again (`RUNUP` in tools/tracks.py). `kart_lift[]` is how high each kart is drawn: `own_kart()` lifts the own sprite and `draw_objects()` the other kart, halved for each size step further away.
- Where things lie: in each track's description in `tools/tracks.py`, as a share of the way round and a sideways offset; the generator snaps coins and panels to the nearest cell of plain road on that side and stops when there is none.
- Obstacles (at most 2 a track): `move_obstacles()` rolls each across the road and back (start, step per frame and frames each way from the track), and sets `ob_struck[]` for a kart closer than 12 px on both axes; `race_frame()` turns that into a hit unless the kart is in the air or falling.
- Moving things are sprites: the other kart, the computer karts, up to 4 shots and up to 2 obstacles, projected into each half by `draw_objects()` with the same camera as the floor: rotate the offset from the camera (4 products), hide it when it is 512 or more map pixels from the camera on either axis, nearer than 56 pixels ahead, or outside the 90 degree view, then the ground line and size from `proj_sl` (by distance / 2), the column from the divider, and for a kart one of 5 views and its mirror from its heading against the line of sight (`proj_bear`). Each kind and size has a record in `obj_frames.bin` (box, ground row, large flag, palette, whether it mirrors, a spare byte, the tile of each of 5 views; 16 bytes a size, 48 a kind): kart 1 at offset 0, kart 2 at 48, shot 96, obstacle 144, then the four computer karts at 192, 240, 288 and 336 (animal A or B, palette 6 or 7; the mid frames for the near and mid sizes, far views 0, 2, 4 for the far size with views 1 and 3 shown as 0 and 4; small, no large flag). The leader shot's comet is the record at 384 (three sizes, palette 5, small, no views): a shot whose `shot_on` is 2 or more takes it instead of 96, and it is exempt from the `CPU_FAR` limit that applies to records from 192 to 383. A kart is a record whose "mirrors" byte (the view flag) is not 0: `draw_objects()` reads it for the shrink, the lift and the views, so a new kart kind needs no change there; a record at 96 or more is drawn small with its high OAM bits left alone (x below 256). The things of a view are rows of 12 (`pj_slots` and its tables): 0 to 5 the karts (the kart's number), 6 to 9 the shots, 10 and 11 the obstacles. A computer kart is drawn once its animals' frames are in video memory (`cpu_gfx_ready`), only for the first `cpu_n` of them, and only up to 360 map pixels ahead of the camera (`CPU_FAR`), because a thing farther away has its top on the HUD lines; a computer kart that fell in, spins, hops, shrinks or is lifted is drawn by the kart rules of a player's. Measured: 4.1 to 4.6 lines per thing with both karts, 4 shots and 2 obstacles in view, on three emulators; 4.3 to 4.4 lines for each computer kart in each half.
- Shots move in `move_shots()`: 4 px a frame, bouncing where a drivable surface meets off-road (surface 0, read through `cur_surf`) and at the map edge. A shot flying mostly along one axis that meets grass where the road goes on 8 px to one side only (a corner) turns that way instead, so a shot thrown down a straight follows the corner rather than flying back at its thrower; a shot ends on the first kart within 10 px (its thrower only after 20 frames) and sets `shot_struck[]`, which `race_frame()` turns into a hit.
- Items: the panel draws 0-15 from an LFSR (`rng`, stepped every race frame and every frame of the title, select, track menu, results and podium screens, so the first race after power-on does not always get the same computer animals) into `odds[]` (48 entries): the leader's 16, second place's 16 (the strong items: boosts, shots, homing shots, triples, the star, the shrink) and a third 16 for places 3 to 6 (3 each of boosts, triple boosts, homing shots and stars, 2 shrinks and 2 leader shots); every one of the 15 items is in one of the tables, and no two tables give the same item at one index, so a test can tell which table a draw used. First place draws from the first, second place from the second (a two-player race, and a battle, only ever has these two), places 3 to 6 from the third, computer karts like players. An item aimed at another kart (the homing shot, the shrink, the steal) goes to the other player in a two-player race or a battle (`cpu_n` 0); with computer karts racing, `target_of()` picks the kart directly ahead in place, or for the leader the one directly behind; a kart that has finished is passed over for the next one that has not (further ahead, or further back for the leader), and when every other kart has finished the choice stays the kart directly ahead or behind. `leader_of()` does the same for the leader shot. The HUD picture cycles through the first four for 60 frames, then X uses the item. `use_item()`:
  - First set: boost 2 s at top speed + 16 (also on grass), shot, slime dropped 24 px behind into a free cell (4 at most, the oldest goes, shared with fake panels), coins + 2.
  - Homing shot: a shot with `shot_home` set to 1 + the kart it chases. `steer_fast()` (proj.asm) turns one shot a frame (each every 4 frames) 4 of 128 steps towards the side the other kart is on (the sign of a cross product); its heading is kept in `shot_ang`, and a bounce or a corner turn made by `move_shots()` is taken back into it first by the same routine (axis turns, mirrored headings); a heading it cannot match makes it a straight shot. `shot_step[]` holds the x step for each heading (y is minus the entry 32 further), because tcc-816 divides with a library call.
  - Triples (boost, shot, slime): `uses[]` starts at 3 when drawn; the triple picture stays for two uses, then the single item shows for the last.
  - Shield: 10 s (`shield_t`, 16 bits); its picture stays in the item box, which takes no panel meanwhile; the first hit or shrink ends it instead.
  - Star: 6 s (`star_t`, 16 bits) of boost (`boost_t` kept at 2 or more), no hits (oil, water and pits still catch it), and touching the other kart hits it; the own kart flashes between its palette and the yellow text palette every 4 frames.
  - Jump: 36 frames in the air through the ramp code (`air_t`, `air_len`), so it clears slime, water and the other kart (`bump_all()` skips a kart in the air); a shot that reaches a kart in the air ends without hurting it.
  - Shrink: the other kart for 240 frames (`shrink_t`): `drive()` holds it to speed 26, boosting or not, its own sprite uses the mid-size frames and `draw_objects()` draws it one size smaller in the other half.
  - Steal: takes the other kart's item and its uses; with nothing to take, it is kept.
  - Fake panel: dropped like slime, drawn with the panel's floor tiles, and a kart that takes it is hit.
  - Leader shot (`ITEM_LEADER` 15, picture a glowing comet drawn in gen_assets.py, in the item box as the 15th HUD picture): `fire_shot(p, 2)` takes a shot slot like any shot and sets `shot_on` to 2 + the kart it flies to, `leader_of(p)`: the kart in first place, or the kart in second when the holder itself leads. `move_shots()` (`_ms_lead`) moves it LEADER_STEP (96, 6 px) towards that kart's position on each axis every frame, at most (a homing shot flies 4 px), whatever lies under it: grass, water, the infield; nothing stops it but its life of 360 frames. When it is within 10 px of the kart on both axes it ends and `shot_struck` is set: `hit()` spins the kart, costs 2 coins, a shield takes the blow and a star ignores it. A kart in the air or sinking is passed under: the shot waits over it (it follows the kart if it moves on) and hits when the kart is on the ground. Only the target kart is touched on the way. `draw_objects()` draws a shot with `shot_on` 2 or more with the record at offset 384 (the comet's three sizes, palette 5), at any distance up to the 511 px of a shot. Kept (not fired) until `leader_ready`.
- Slipstream (`slipstream()` in proj.asm): every other frame one kart, so each every 4 frames. When the other kart is within 12 px (both axes) of the point 24 px ahead (the slime drop's table `drop_d`, no multiply) at speed 24 or more, `slip[]` counts up; 15 ticks in a row (about 1 s) give a 40-frame boost.
- A hit (`hit()`) spins the kart for 64 frames through its 8 views (`spin_off`, which `draw_objects` also adds to the heading), ends its tricks and costs 2 coins. Two coins add one step of top speed, up to 10 coins.
- Effects at the own kart (slots 56-59): sparks at the wheels once a drift is charged, flames beside the wheels while boosting. They sit beside the kart, because the own kart's sprite (slot 0 or 1) is drawn in front of every later slot.
- Tricks: the pedal down at most 20 frames before GO gives a 45-frame boost; pressed earlier and held, the wheels spin 45 frames. L or R hops (8 frames, sprite lifted); landing with L or R held and the D-pad pushed starts a drift that turns its way (half again when steered into, half when steered out) and charges; letting go with charge 40 or more gives a 40-frame boost. Sparks show once charged.

## Race rules

- Lap progress: each 16x16 cell of a track holds how far round the lap it lies, 0 to 254 from the start line (the nearest point of the centre line, or of the shortcut, whose cells run from its start's value to its end's), or 255 more than 40 px beyond the road edge, where nothing counts. Checkpoint = progress / 8: 32 a lap (`NCP`), 70 to 115 px apart. `progress_players()` reads one cell per player: the checkpoint only moves to the next one, so cutting across reaches a later checkpoint out of order and gains nothing, and a lap counts when checkpoint 0 is reached. Karts start on checkpoint 31. A computer kart's progress is read by `progress_cpu()`, one kart a frame in turn (a kart moves about 10 px in the 4 frames between its reads, less than a progress step of about 14 px).
- `lap` counts start-line crossings: 1 during the first lap, 4 once finished; reaching lap 3 shows "FINAL LAP" in green for 1.5 s (`final_lap()`, counted in `finals[]`). Position compares `prog` = (lap x 32 + checkpoint) x 8 + `frac`, where `frac` is 8-15 inside the checkpoint and 0-7 a little back in the one before; it is kept off the track, so a cut across the infield does not swap places. If both karts finish on the same frame, player 1 wins. A kart that finishes takes the next place (`lap_next()` in proj.asm); the first player home starts the 10 s to the results (a computer kart finishing starts nothing: the race goes on until a player is home), and the race ends 1.5 s after both players are home at the latest; `main()` shows the results when the timer is out and a player has finished (or a battle is decided). `winner` is the first player to finish. A computer kart that has finished takes no coins, panels or slime (`floor_scan()` skips it) and uses no item (`cpu_item()` returns at once). A kart still racing is placed behind the finished ones by progress. The HUD shows the place as "1ST" to "6TH": the number, then S, N, R or T, then T, D or H; the R has no HUD letter and is a tile of its own (`TILE_GR`). The results screen writes the same names for any place.
- Wrong way: `wrong[]` counts steps of progress backwards in a row (a step forward clears it); at 3 the sign shows in that half (`wrong_way()`), and it goes once the kart drives forward again.
- The minimap: each half shows the track's 32x32 minimap at (8, 76) of the half, and `minimap()` places each kart's dot at map position / 32.
- Karts closer than 10 map pixels on both axes are pushed apart and lose a quarter of their speed (`bump_all()`); the push is split half and half, except that a kart standing still (speed under 3) is not shoved and the other kart takes all of it (`_bm_share`), so a parked kart stays where it is. The map edge holds a kart and leaves it speed 3, enough to steer away (`keep_all()`). Places rank by progress over every kart racing, and the lower number is ahead on a tie (`rank_all()`; with computer karts racing it works every 4th frame, so a place changes up to 4 frames late; the results screen runs one full pass first).
- Battles (`battle` 1 balloons, 2 coins) run on the arena, track 4, picked as BALLOON BATTLE or COIN BATTLE from the track menu (rows 5 and 6); there are no laps, checkpoints or lap letters. Balloon battle: 3 balloons each (`balloons[]`); `pop()` takes one on every hit and every fall (`pops[]` counts them), and the kart left with none loses (`battle_over()`, results 1.5 s later). Each half shows its own balloons over the own kart and the other kart's over it when in view; their pictures are copied over the lap and banner letter frames at race start. Coin battle: 60 s on a clock in each half, coins count to 99 (their speed bonus still only to 10), a taken coin comes back every 2 s one at a time from the arena's list (`trk_coins`), the most coins win and a tie goes to the last kart to take the lead (`lead_p`, also handed over when a hit costs the leader its lead). During a battle the kart with more balloons or coins counts as first for the panel draws (both as behind on a tie); the results show the counts from the moment it was decided (`final_count`), not what the 1.5 s before them changes. A kart sinking into a pit is not hit by shots or a star kart's touch.

## Computer karts

- Data: karts 0 and 1 are the players, 2 to 5 the computer karts. Every per-kart array holds 6 (`NK_MAX`); `cpu_n` (a RAM byte, 0 to `CPU_MAX`) says how many computer karts race, and every loop visits 2 + `cpu_n` karts. With `cpu_n` 0 none of the computer karts' work runs and the race is the two-player race it was; every check outside the computer-kart race runs that way. The track menu sets `cpu_n` from `cpu_menu` (see Screens). `start_race()` holds `cpu_n` to `CPU_MAX` (main.c, 3 now; the tests' `CPU_FIT` is the same number). It is not the one number to raise: the results screen has rows for 5 karts (a sixth would land on the START line), the budget below is measured with 3, and the race data holds 4 computer karts and a battle to 0. All six karts are set up at every race start, on the six places of `trk_grid` (see Tracks), facing along the road, each with its animal's kart type (`cpu_pick`).
- What runs for a computer kart: the driving (below), the countdowns, the floor (ramp, oil, water, a pit and its rescue), the pickup scan (it takes coins, and panels with the odds of its place), the bump against every other kart, the map edge, the shots, the obstacles, the star's touch, the lap progress and the place. A panel starts the kart's item roll and its decision countdown (see Computer karts' items). A hit spins it and costs coins, a fall into water or a pit puts it back at its checkpoint's rescue point (`rescue()`), oil spins it. Only the players have a HUD: `hud_coins()`, `hud_item()`, `hud_lap()`, `hud_place()`, `wrong_way()` and the banner leave a computer kart alone.
- Driving: `cpu_frame()` (proj.asm, called from `race_frame()` right after the players' `drive()` when `cpu_n` is not 0) drives every racing computer kart one frame, from GO on (nothing before it, no rocket start) and unless `cpu_hold` is 1 (the tests' `calm()` sets it, so every check outside the driving checks sees parked karts; the game never sets it). Per kart: the steering map's byte for the kart's 16x16 cell (the index `progress` reads) gives bits 0-6, the heading to aim at (0-127, the game's angle units); the kart's own bias is added (`cpu_bias`: kart 2 -3, kart 3 +3, karts 4 and 5 0 steps, about 2 px sideways a step on a straight, so the karts spread over about 12 px and do not stack on one line); it turns right when its heading is 2 to 63 steps short of that, left when 2 to 126 steps past it, not at all within one step; it presses the pedal, except where bit 7 marks a tight stretch and it is above speed 30 (`CPU_SLOW`), where it brakes instead and so holds about 30. Then the physics are a player's: `dr_run` (the body of `drive()`), the kart's own type, coins and boosts, no rubber-banding and no speed bonus; a kart with no timer running (spin, fall, wheelspin, boost, shrink, air, drift all 0) on plain road takes a short copy of the same rules inside `cpu_frame()` (surface read once, top speed from the type and the coins, pedal, brake, steering, `mk_move`), every other state goes through `dr_run`. Ramps are taken at speed, and a spin, a fall, oil and the map edge work as for a player. A finished kart keeps driving on the map, so it never stops on the line.
- Steering round a kart in the way: when a computer kart touches any kart (`bump_all()` calls `_bm_swerve` for each computer kart of a touching pair), it aims `AV_T` 30 frames (half a second) to one side of the steering map's heading, 14 of 128 steps (`AV_R` or `AV_L`; `cf_av` holds the frames left and `cf_sd` the side for each computer kart, `cpu_frame()` adds it to the aim and counts it down) and turns that far at once, because a kart held up by the other kart is too slow to steer clear. The side is the one with road: the surface 30 px to the right and to the left of the other kart (two of the computer kart's forward steps from `mk_tab` at speed 15, across its heading) is read, and when only one is plain road it takes that one; when both or neither are, it takes the side away from the other kart (the sign of a cross product, done with the 8 x 8 multiplier). A kart already steering round keeps its side and only gets its 30 frames back; all counts are cleared before GO. Cost: the first touch of a pair costs about 100 instructions (under 4 lines) once, and a frame with no touch costs one compare a kart. Without it a computer kart that drove into a stopped or slow kart (a player who has not pressed B, one on the map edge, a spinning kart) pushed it along the road for the whole race.
- The steering map (`tools/tracks.py steer_map()`, `res/trkN.steer`, 4 KB a race track, `cur_steer` set by `load_track()`): one byte per 16x16 cell. Heading: from the cell's centre to the centre-line point 40 px (`AIM`) beyond the cell's nearest sample of the main route (never the canal shortcut or the bay), for every cell, road or not, so a kart off the road steers back; a track's `dodge` list (Sandy Twist) moves that aim point sideways for 30 px each way and eases it back over 45 px, so the karts pass the oil and the sand that lie on one side of the road (the generator stops when the dodged line is not plain road). Bit 7: the tight mark, set where the tightest bend within 60 px (`LOOK`) ahead, measured through the route samples 40 px either side of it, has a radius under 93 px, the circle the heavy kart can hold at its top speed (top 41 / 16 px a frame over turn 144 / 256 x 2 pi / 128 radians a frame = 92.8 px; light 72, medium 82). The generator exits with an error when on any road cell of the main route the heading points against the race direction (the widest angle it accepts is under 90 degrees; the tracks show 44 to 88). `python3 tools/tracks.py DIR` draws the arrows over each track. The ROM holds 16 KB for it (the arena has none: battles have no computer karts).
- Computer karts' items: a panel a computer kart drives over (with the odds of its place) sets `roll[p]` and `cpu_use_t[p]` to `ROLL_FRAMES`; `kart_timers()` (proj.asm) counts `cpu_use_t` down for every racing kart (players' stay 0) and at 0 sets the kart's bit in `cpu_due`. `cpu_item(p)` (main.c) then does everything C has to: it ends the roll (item set, `uses` 3, no HUD: `hud_item()`, `hud_coins()` and `hud_lap()` return for a kart above 1), and decides whether to use the item now, by item (`base` is the single item of a triple):
  - at once: coins, star, shield;
  - boost, triple boost: on a floor cell whose steering byte has no tight mark (bit 7);
  - shot, triple shot: when another kart lies within 160 px ahead and within 24 px of its line (`cpu_sees()`: four products against the heading, kept to karts within 160 px on both axes);
  - slime, triple slime, fake panel: when a kart lies within 120 px behind it and within 24 px of its line;
  - jump: when the surface 24 or 48 px ahead is oil or water or a pit (`cpu_wet_ahead()`);
  - homing shot, leader shot, shrink, steal: after a random 30 to 120 frames (`cpu_age` holds the delay chosen, `rng & 127` less 91 when over 90);
  - anything not yet usable is looked at again every `CPU_RECHECK` 8 frames and used anyway once it has been held `CPU_PATIENCE` 300 frames (5 s); a spinning or sinking kart uses nothing until it is back; an item that could not be used (slime with no free cell, a steal with nothing to take, a jump already in the air, a leader shot before its picture is loaded) is tried again and dropped after 5 s.
  The use is `use_item(p)` and aims with `target_of(p)`, so an item does to a player what a player's item does to the other player: a computer kart's steal takes the player's item and empties the player's item box (`hud_item(o, 0)`), a shot spins the player it hits. After a use that leaves the item (a triple's next use, or a stolen item) the countdown restarts at 45 frames; `cpu_used[p]` counts the uses (the tests read it). The decisions never write the players' sprite slots.
  A decision costs 10 lines for the simple items and up to 40 for slime or the fake panel (measured on snes9x, as extra lines on a quiet frame: coins 12, boost 10, star 10, shield 10, jump 13, steal 12, shrink 18, leader shot 23, homing shot 29, shot 30, slime and fake panel 40), too much for the finish frame. So `race_frame()` runs one decision a frame, the lowest due kart, at the very end of its work and only when `frame_lines()` (proj.asm, the line counter as `measure()` reads it) says the frame has used fewer than `CPU_GATE` 136 lines; a busier frame leaves the bit in `cpu_due` and the next lighter frame takes it. The dearest decision on a frame under the gate then still ends under 180. The gate reads the line counter, which differs a little between emulators, so the frames the decisions land on, and with them the races, differ a little between emulators (items used per kart in the three-kart race on the oval: 3 to 8 on each).
- Drawing: see Things on the track. Computer karts that cannot be told apart in depth (a nearer one can be covered by a farther one with a lower slot) are not sorted.
- The budget, measured with the computer karts driving (`cpu_hold` 0) by the busiest frame of the tests (the finish: the other kart, 4 homing shots and 2 obstacles in view, the banner and the place changes, four times with the finish a frame later each time; the computer karts on the road ahead of both players in view of both halves, in their costly states: the first on the grass beside the road, the second spinning (in line in front of the first), the third boosting, the fourth plain on the road; the first one's item decision due on every frame), in lines of 262 on snes9x2002, snes9x2005 and snes9x (budget 180):

  |---|---|---|
  | 0 | 127 / 132 / 136 | 127 / 132 / 136 |
  | 1 | 153 / 153 / 159 | 153 / 149 / 154 |
  | 2 | 164 / 171 / 177 | 155 / 162 / 168 |
  | 3 | 178 / 186 / 193 | 165 / 172 / 179 |
  | 4 | 195 / 204 / 212 | 177 / 185 / 193 |

  The same scene on each race track with three computer karts and alternate frames (`cpu_drive_block()` runs it after the driving checks; measured on snes9x2002 / snes9x2005 / snes9x): Clover Oval 165 / 172 / 179, Sandy Twist 166 / 173 / 180, Frosty Peaks 166 / 172 / 179, Moon Harbour 166 / 173 / 180. The busiest track leaves no line on snes9x (180 of the budget 180); no change to the code was needed to hold it.

  Three computer karts fit with alternate frames (`CPU_MAX` 3, `cpu_alt` 1 by default) and leave 0 to 1 lines on snes9x (the slowest of the three; 1 on the oval, 0 on Sandy Twist and Moon Harbour); four do not (193). The costly states (a kart on the grass, spinning or boosting goes through `dr_run` instead of the short path in `cpu_frame()`, and draws and bumps differently) added 7 lines to the road-only scene of step 5 (176 to 183 on snes9x with 3 karts); making room took them out again: `mk_move` reading `mk_tab` instead of multiplying (3 lines with 3 computer karts, since 5 karts move) and `race_frame()` calling `kart_frame()` only when a player has something for it (1 line). - `cpu_alt` (a RAM byte, 1 now: set in `main()`, and three computer karts fit only with it): with it set `draw_objects()` projects each half's computer karts only on every other frame (`race_time` and the half's number say which), so each sprite is updated at 30 Hz and the other frames leave it where it was. It halves the draw of the computer karts (the table above), and a computer kart seen while the camera turns is a frame late: 3 pixels at most at the medium kart's turn (6 pixels off the exact place against 3 when every frame is projected, measured by the test; about 4 for the light kart, 128 x the turn per frame). A cap on the things projected per half per frame (a third option) costs the same as alternate frames for 4 karts and more for 3, so it is not built. The checks of the computer-kart race set it to 0 (`cpu_calm()`) to look at one frame, and the ones about it set it themselves.
- Sprites per screen line, counted by the test from the OAM copy on the same frames (karts spread in depth): at most 14 sprites and 28 tiles with one computer kart, 16 and 32 with four, against the limits of 32 sprites and 34 tiles a line. Stacked, the finish banner (16 tiles), 4 shots and 2 obstacles (12) and four computer karts on the same lines (8) make 36 tiles, which is over: the hardware drops tile slivers on such a line.

## Units

- Kart position: 1/16 map pixel in `s16` (0 to 16383). Speed: 1/16 pixel per frame. Angle: `u16`, where `(angle >> 8) & 127` is the table row and 0 faces up the map.
- `frames_done`, `max_lines`, `phase_best` and `phase_cnt` (the per-phase table, filled only in a `PROBES` build), the race state (`game_state`, `lap`, `cp`, `frac`, `finished`, `place`, `winner`, `finish_time`, `race_time`, `bumps`, `karts`, `oamMemory`), the track and the cup (`track_no`, `menu_pos`, `cup_on`, `cup_race`, `points`, `cup_winner`, `cpu_menu`, `fine`, `wrong`, `banner_t`, `finals`), the track features (`air_t`, `air_len`, `trick`, `trick_t`, `fall_t`, `kart_lift`, `rescues`, `ob_on`, `ob_x`, `ob_y`, `ob_dx`, `ob_dy`, `ob_len`, `ob_t`, `ob_struck`), the picks (`pick`, `cpu_pick`, `cpu_n`, `cpu_hold`, `cpu_alt`, `cur_steer`, `cpu_loaded`, `cpu_gfx_ready`, `leader_ready`, `cursor`, `locked`, `refuse_t`, `kart_type`, `accel_frac`), the things on the track (`cells`, `coins`, `item`, `roll`, `last_roll`, `cpu_use_t`, `cpu_due`, `cpu_age`, `cpu_used`, `boost_t`, `spin_t`, `spin_off`, `hop_t`, `wheelspin_t`, `drift`, `charge`, `hits`, the `shot_*` arrays, `pj_lines`, `pj_count`) and the tables `kart_types`, `odds` (48 bytes: three tables of 16) and `floor_set` are read by the tests by symbol name: keep the names. The tests also read VRAM, to check the loaded sprite tiles, the names on the Mode 1 map and the floor cells. The tests also write `karts`, the item state and the shots to set up each check.

## Adding a track

- Add a description to `TRACKS` in `tools/tracks.py` and preview it. The start line must lie on a straight; keep the centre line 64 px from the map edge, and the map corner at (1016, 1016), which holds the sky tile, off the road. Two parts of the road need about 64 px of off-road between their edges, or the lap progress lets a kart cut across.
- Tile 0 is plain off-road (it also fills everything outside the map); the generator keeps every track within 256 tiles and stops if a coin, panel or pad has no plain road, or a track has other than 4 panels or more than 2 obstacles.
- A fifth track also needs a row in main.c's `menu_row` and a menu that fits it, and changes the cup (`CUP_RACES`); the ROM is 512 KB and uses about 503 KB (515,518 bytes: the last byte that is not padding, summed over the sixteen 32 KB banks of this build), so about 8.6 KB (8,770 bytes) is free, and a track (about 62 KB of tiles, map, surfaces and the rest) needs the 1 MB ROM.

## Retro game sticks

Some retro game sticks with built-in emulators run Super Nintendo games on the Snes9x 2005 libretro core. Among the three test emulators that is `snes9x2005`. On the busiest frame it measures 7 lines lighter than `snes9x` (172 to 173 against 179 to 180), so the 180-line budget stays measured on `snes9x`, the slowest of the three, as the margin.

- The game's header declares no SRAM, so it saves nothing.
- Some sticks list their games in an index of their own, and a copied game file shows in the menu only once the index names it. This folder has nothing for adding an entry.
